# Security

Supabase Auth is the identity provider. Admin eligibility is stored in `admin_users`, never inferred from a client role or any authenticated session. It is enforced by the `is_admin()` RLS helper, the `/admin/*` proxy check, and the protected admin layout's server-side `requireAdmin()` check. Anonymous visitors may view active catalogue data only.

The admin login accepts email/password only at `/admin/login`; there is no customer registration route. A server action validates input, applies a server-side rate limit, authenticates with Supabase Auth, checks `is_admin()`, and server-redirects only for a valid administrator. Authentication and authorization failures use the same generic message. A signed-in non-admin is signed out and does not receive admin access. Sign-out uses the server Supabase client, clears Supabase-managed session cookies, and redirects to login. Redirect destinations are fixed internal paths, not user-controlled values.

When Supabase reports an explicit invalid or missing refresh token in the `/admin/*` proxy, the app clears only cookies matching the current project's `sb-<project-ref>-auth-token` session name/chunks. The request then behaves as unauthenticated; `/admin/login` remains renderable and protected routes redirect there. Other auth/network errors do not trigger broad cookie deletion. Token values are never logged or exposed.

The sign-in limiter is a process-local, in-memory limiter keyed independently by IP, a SHA-256 email hash, and the combined pair. It is configured by `ADMIN_LOGIN_RATE_LIMIT_MAX_ATTEMPTS` (default `5`) and `ADMIN_LOGIN_RATE_LIMIT_WINDOW_SECONDS` (default `900`). It applies only server-side and never stores passwords. It reduces abuse on a single instance but is not distributed across serverless instances; use a managed/distributed limiter before relying on it as the sole production-wide control. `x-forwarded-for` is meaningful only when supplied by a trusted deployment proxy.

All mutating endpoints must use Zod validation, perform authorization server-side, and derive prices/totals from the database. Paystack secret keys remain server-only; payment success is accepted only after server verification and idempotent reference handling. Never expose orders/customers by public ID alone.

CI/CD is deferred. Any future implementation must scan for common Paystack/service-role secret forms, reject public-prefixed server-secret variable names, preserve `server-only` boundaries, and use no payment, Supabase service-role, database-management, or Vercel deployment credential. See `docs/future/CI-CD.md` for the deferred requirements.

`.env.local` is ignored; `.env.example` contains names only. `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_ANON_KEY` are browser-safe project configuration. `SUPABASE_SERVICE_ROLE_KEY` and `PAYSTACK_SECRET_KEY` are server-only and must never have the `NEXT_PUBLIC_` prefix. Future sensitive routes require rate limiting and defensive logging. Avoid collecting data beyond order contact and fulfillment requirements.

Phase 2 corrected an overly broad settings policy: the applied migration removes anonymous access to operational settings. During the 2026-08-11 audit, the remote REST API exposed the migrated catalogue/orders endpoints. Actual RLS behavior against rows and real administrative authentication still awaits dedicated remote test identities. Never use the service-role key as a substitute for project-management or database-password access.

Phase 3 catalogue requests are server-side anon-key requests subject to the same public RLS policies as the storefront; no customer catalogue request uses the service-role key. Shop query parameters are constrained by Zod before becoming Supabase filters. Product descriptions render as escaped text rather than raw HTML. Customer-facing catalogue errors are generic and do not expose database error details. Only the public Storage bucket configured by `SUPABASE_PRODUCT_IMAGES_BUCKET` can produce product image URLs.

Anonymous live API verification on 2026-08-13 returned the public categories and an empty public products result. An anonymous orders query also returned an empty result, consistent with the no-public-orders policy; no sensitive order payload was exposed.

Phase 4 catalogue actions are another server-side trust boundary: every action calls `requireAdmin()` before reading or mutating rows, then operates through the authenticated SSR client and existing admin RLS policies. UI controls, hidden IDs, category IDs, product IDs, variants, booleans, prices, and stock values are all untrusted input. Zod validates their shape; product/variant IDs are re-read under RLS; submitted variant IDs must already belong to the target product; and products may only be assigned to active categories. Database constraints remain the final guard for unique slugs/SKUs and non-negative integer money/stock values. Errors are generic and never contain database details.

Phase 5 treats the guest cart as untrusted convenience state. Local storage contains only a versioned product UUID, variant UUID, and bounded integer quantity—never prices, totals, stock, delivery fees, customer details, or any authentication token. The checkout Server Action Zod-validates the cart and guest fields, reloads active products/variants via normal public RLS, verifies that each variant belongs to its requested product, and calculates all money values in integer kobo. Client-supplied prices, totals, stock, availability, and fees are not accepted. Customer text is length-limited and React-escaped; Phase 5 does not log, persist, or render it as HTML. It neither creates an order/customer nor reserves/decrements stock, so a later payment/order phase must revalidate again.

Phase 6 uses the server-only `SUPABASE_SERVICE_ROLE_KEY` solely for the private payment data-access module; it is never imported by client code. Paystack is initialized and verified on the server with `PAYSTACK_SECRET_KEY`. The callback reads only a reference and never treats its visit as success. Its result redirect is a fixed path built from the configured `PAYSTACK_CALLBACK_URL` public origin, never from query parameters or an untrusted proxied Host header. For a syntactically valid reference it renews the existing opaque payment-reference cookie with `HttpOnly`, `Path=/`, `SameSite=Lax`, and `Secure` whenever the configured public origin is HTTPS; only the server-side result page reads it. The webhook authenticates its raw body with a timing-safe HMAC-SHA512 check before parsing, handles only `charge.success`, and then calls Paystack verification. Fulfilment additionally requires matching reference, amount, currency, and transaction success. The migration’s reference/idempotency constraints plus locked, conditional stock deduction make duplicate callbacks/webhooks and races safe. The browser holds only an HttpOnly opaque payment-reference cookie for its own result view; it is not an order/customer lookup API.

The applied `product-images` Storage migration creates a public-delivery bucket with a 5 MiB JPEG/PNG/WebP allowlist. Object mutation requires an authenticated `is_admin()` session and the `products/` prefix. The server action separately validates MIME type, size, first-byte file signatures, current product access, and server-generated product-scoped random paths; browser-provided paths are ignored. No service-role key is imported. Server Actions retain Next.js Origin/Host CSRF protection; deployment must configure allowed origins if it uses a different proxy host.

On 2026-08-14, live anonymous category/product reads were reachable under public RLS and anonymous category/product REST mutation probes returned HTTP 401. The linked RLS-policy verification SQL completed successfully. Public `orders`, `customers`, `admin_users`, and `settings` reads returned no rows in the current empty live project; this does not replace a controlled row-level test. Authenticated admin/non-admin and Storage-object policy scenarios still await the browser/session verification surface.
