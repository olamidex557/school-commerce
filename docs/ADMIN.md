# Admin

Admin login is at `/admin/login` and uses Supabase email/password authentication through a server action. All other `/admin/*` routes require both a valid Supabase session and an `admin_users` row whose `user_id` equals the authenticated user's `auth.uid()`. A signed-in non-admin is signed out and receives the same generic sign-in failure as an invalid login. The proxy and a server-rendered protected layout both enforce this; database RLS independently protects data. The current protected page is intentionally only an authorization-foundation placeholder.

Expired, revoked, or otherwise invalid refresh-token sessions are recovered in the proxy by clearing that project's Supabase SSR cookie chunks and treating the request as signed out. Valid sessions are not broadly cleared.

To authorize an administrator after migrations are applied: create the user in Supabase Auth, then insert that user's UUID into `public.admin_users` from the SQL Editor or another privileged administrative connection. Do not expose a public UI for this operation. Planned sections are dashboard, orders, products, categories, customers, and settings.

Current catalogue routes are `/admin/products`, `/admin/products/new`, `/admin/products/[id]`, and `/admin/categories`. They support product/category creation and editing, active/archive state, featured state, category counts, active variants, integer-minor-unit prices, stock quantities, image upload/removal, and a public storefront preview link. New products start as simple catalogue records with no generated variant; add a variant only when it needs its own name, SKU, price, and stock. Every explicitly added variant requires all four values. Variants omitted from a saved edit are archived (`is_active=false`) rather than deleted. Categories cannot be archived while they have active products. Product deletion is intentionally absent.

`/admin/orders` and `/admin/orders/[id]` provide protected order operations. The list supports bounded search/filter/sort/date URL state and pagination; detail shows immutable fulfilment/customer/item/price snapshots, safe payment-attempt metadata, and operational history. An administrator may only progress `paid → confirmed|cancelled` or `confirmed → completed|cancelled`. Payment state, Paystack references/transaction IDs/amounts, verification timestamps, snapshots, and stock are read-only; cancellation is not a refund or stock reversal.

The Phase 7 migration was applied to the linked project on 2026-08-19. Schema/policy checks and an anonymous denial probe passed without changing any order, payment, or stock record. Using the dashboard against real data, or exercising transitions, remains pending controlled administrator/non-admin sessions and a disposable approved test order; do not use existing customer orders as test fixtures.

Images use the `product-images` Supabase Storage bucket. The server, not the browser, generates product-scoped paths and validates file signature/type/size. The first image by `position` is primary; upload appends a new position, and removal deletes the Storage object and its metadata row. Reordering is not implemented yet. Dashboard, customers, and settings UI remain future work beyond the implemented catalogue/order operations.
